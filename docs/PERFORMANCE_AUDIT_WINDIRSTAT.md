# 성능 메모

이 문서는 **기본 분석**과 WinDirStat 등과의 **성능·전략 차이**를 짧게 정리합니다. 실험 진단의 실측 수치는 환경에 따라 다릅니다.

WinDirCleaner의 기본 분석은 일반 파일 열거입니다. WinDirStat처럼 NTFS 전용 빠른 경로를 기본값으로 쓰지 않습니다.

같은 드라이브라도 파일 수에 따라 체감 시간 차이가 큽니다.

| 항목 | WinDirCleaner | WinDirStat |
|------|---------------|------------|
| 드라이브 목록 | 이름·유형 먼저, 용량은 별도 조회 | 일반적으로 빠름 |
| 전체 드라이브 분석 | 순회 기반이라 오래 걸릴 수 있음 | NTFS 빠른 경로가 있다고 알려져 있음 |

앱 쪽에서 하는 일:

- 드라이브 용량은 드라이브별로 조회합니다.
- 상세 분석은 UI 스레드 밖에서 실행합니다.
- 결과 목록은 진행 중 필요한 만큼만 갱신합니다.
- 폴더를 지정하면 범위를 줄일 수 있습니다.
- “빠른 상세 분석”은 **바로 아래 항목** 단위로만 제한적으로 병렬 처리합니다.

WinDirStat은 GPL-2.0입니다. 코드를 가져오거나 포팅하지 않습니다.

## 진단 결과 해석 기준(참고 지표)

아래 수치는 **환경·권한·캐시·부하**에 따라 달라지며, 단정적인 성공/실패 임계값으로 쓰기 어렵습니다. **다음 의사결정에 쓰는 참고 지표**로 보는 것이 맞습니다.

| 지표 | 무엇을 보나 | 참고 관점 |
|------|-------------|------------|
| `ParsedRecords` / `TotalRecords`(원시 슬롯) | 고유 FRN으로 정리된 비율 | 비율이 지나치게 낮으면 중복·누락·파싱 경로를 점검할 가치가 있음 |
| `UnsupportedVersionRecords` | USN_RECORD 버전 2 외 항목 | 0이 아니면 파서·OS 버전 대응을 검토 |
| `InvalidRecords` | 파싱 실패 건수 | 0이 아니면 레코드 경계·버퍼 처리 등을 검토 |
| `OrphanRecords` | 부모 FRN을 찾지 못한 항목 | `ParsedRecords` 대비 비율이 크면 트리 재구성 정확도를 추가 검토 |
| `SuccessRate` | 샘플 크기 조회 성공 비율 | 높을수록 OpenFileById 경로가 유망해 보일 수 있음 |
| `AccessDeniedRate` | 권한 거부 비율 | 높으면 샘플·추정이 실사용과 어긋날 수 있음 |
| `FailureRate` | NotFound·기타 실패 합산 비율 | 높으면 핸들/경로·레이스 등 원인 조사 필요 |
| `FilesPerSecond` | 샘플 처리 처리량 | 샘플 수·stride·캐시에 민감 |
| UI의 전체 조회 추정 시간 | 직전 트리의 `FileRecords` ÷ `FilesPerSecond` 선형 추정 | **실행하지 않은** 전체 조회에 대한 가늠치일 뿐 |

## 현재 정리(관찰, experimental)

- 일반 순회·제한 병렬 분석은 **WinDirStat식 NTFS 빠른 분석과 다르다.** 큰 볼륨에서는 여전히 시간이 걸릴 수 있다.
- NTFS 진단은 **가능성·속도**를 보여 주었지만, **폴더별 용량 분석으로 통합되지는 않았다.**
- OpenFileById **샘플**은 빠른 편이나, **전체 파일** 크기 조회는 아직 검증·연구 단계이며 추정만 제공한다.

## 파일 크기 실험(OpenFileById)

- USN 기반 **트리 골격**까지는 파일 크기·폴더 용량이 없습니다.
- `OpenFileById` + `GetFileSizeEx`로 **일부 파일**(기본 500, 최대 50,000 샘플)만 열어 가능성·속도·실패 비율을 봅니다. 삭제 기능과는 무관합니다.

### 참고로 좋은 결과

- 500~1,000건 샘플이 짧은 시간 안에 끝난다.
- AccessDenied·기타 실패 비율이 낮다.
- UI가 멈추지 않는다.

### 부담이 크다고 보일 때

- 샘플만으로도 매우 느리거나 거부·NotFound가 많다.
- 이 경우 raw MFT 속성 파싱 등을 검토하거나, NTFS 저수준 경로는 용량 없는 구조 진단에 한정할 수 있습니다.

## 샘플 확장과 시간 추정

### 500건 샘플(참고 실측)

- 성공 499/500, 약 0.046s, 약 10,836 files/s(환경에 따라 다름).
- 같은 PC에서 트리 진단 기준 FileRecords 약 1,466,754개라면, 같은 속도를 가정한 단순 선형 추정으로는 **약 2분 이상**이 될 수 있습니다(캐시·권한·IO에 따라 크게 달라짐).

### 전 볼륨 크기 조회를 바로 넣지 않는 이유

- 핸들·IO 부하와 UI 응답 부담이 있습니다.
- 샘플 수를 늘렸을 때 실패율·속도가 어떻게 되는지 먼저 보는 편이 낫습니다.
- 전체 집계는 코드에 포함되어 있지 않으며, “전체 실행” 버튼도 없습니다.

### 샘플 5,000~50,000 이후에 볼 것

- 10,000·50,000에서도 files/s가 크게 무너지지 않는지.
- AccessDenied·NotFound·기타 실패가 낮은지.
- UI가 응답 가능한지.
- FileRecords ÷ files/s로 본 추정 시간이 팀 기준에서 수용 가능한지.

### 대안

- raw MFT 쪽으로 연구를 옮기거나, NTFS 경로를 구조 진단 전용으로 제한합니다.
