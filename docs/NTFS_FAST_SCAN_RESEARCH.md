# NTFS Fast Scan 메모

이 문서는 **NTFS 실험 진단**(USN 열거, 트리 골격, OpenFileById 샘플 등)의 범위와 한계를 정리합니다. **일반 상세 분석을 대체하지 않습니다.**

일반 상세 분석은 `Directory` / `FileInfo` 기반 순회입니다. 파일이 많으면 시간이 걸릴 수 있습니다.

실험 메뉴는 Microsoft 문서에 정의된 `FSCTL_ENUM_USN_DATA` 등을 사용해, USN 레코드를 읽을 수 있는지와 파싱 가능 여부를 확인합니다.

## 앱 UI의 세 가지 실험 진단

화면의 **실험적 NTFS 진단** 영역은 역할이 다른 세 블록으로 나뉩니다. 각 블록은 **진단용**이며 일반 상세 분석 결과와 합쳐지지 않습니다.

| 구분 | 목적 | 한계(요약) |
|------|------|------------|
| 레코드 열거 | 볼륨에서 USN/MFT 레코드를 얼마나 빠르게 읽는지 | NTFS가 아니거나 권한이 없으면 실패할 수 있음 |
| 트리 골격 | FRN / ParentFRN으로 트리 골격을 만들 수 있는지 | 파일 크기·폴더 용량 집계는 포함하지 않음 |
| 파일 크기 샘플 | `OpenFileById`로 **일부** 파일 크기를 읽을 수 있는지 | 전 볼륨 크기 합산·실제 전체 조회 실행은 아님 |

**진단 요약 카드**에는 마지막으로 실행한 진단 종류·상태·소요 시간·짧은 해석이 모아 표시됩니다. 정리 추천이나 “삭제 가능” 같은 의미는 없습니다.

## 코드에 포함된 범위

- NTFS 여부 확인
- 볼륨 핸들 열기(읽기 전용)
- USN 레코드 개수·소요 시간
- `USN_RECORD` **V2**(major version 2) 파싱
- FRN / ParentFRN 연결 상태 점검
- `OpenFileById` + `GetFileSizeEx`로 **샘플** 파일의 크기 조회 진단(기본 500건, 최대 50,000건까지 선택)

## 포함되지 않는 범위

- 볼륨 전체 파일 크기 합산, 폴더별 용량 집계
- 일반 분석 UI와의 결과 통합
- 삭제·정리 기능과의 연동
- WinDirStat 코드 복사·포팅

USN 레코드만으로는 일반적인 파일 크기를 바로 얻기 어렵습니다. 폴더별 용량은 다른 접근이 필요합니다.

## 파일 크기 샘플 진단(OpenFileById)

### 배경

- `FSCTL_ENUM_USN_DATA` / `USN_RECORD_V2`에는 파일 크기 필드가 없습니다.
- 트리 골격만으로는 용량을 알 수 없으므로, FRN으로 `OpenFileById`를 열고 `GetFileSizeEx`로 읽는 방식이 현실적인지 **샘플**로 확인합니다.

### 동작

- USN에서 **File** 종류만 골라 최대 100~50,000건(기본 500). 5,000 이상은 벤치마크용으로 시간이 늘 수 있습니다.
- 볼륨 핸들을 힌트로 `OpenFileById`(읽기 속성 수준) 후 `GetFileSizeEx`.
- 전 볼륨 스캔이나 폴더별 용량 집계는 하지 않습니다.

### 볼 때 지표

- 성공, AccessDenied, NotFound, 기타 실패 건수
- 시도당 처리량(files/s)
- 샘플 수·환경에 따른 경과 시간

### 한계

- 파일마다 핸들을 열면 느려질 수 있습니다.
- 권한, 공유 모드, 다른 프로세스의 사용 등으로 실패가 늘 수 있습니다.
- 실패율이 높거나 대량 샘플이 부담이면, 전체 용량 산출 전략으로는 부적합할 수 있습니다.

### 샘플 규모·추정 시간

참고 실측(한 PC, NTFS `C:`):

- 트리 골격 진단: 완료 약 6.27s, TotalRawSlots 약 1,807,262, ParsedRecords 약 1,806,707, Unsupported/Invalid 0, Orphan 약 45.
- 파일 크기 샘플 500건: 성공 499/500, 약 0.046s, 약 10,836 files/s.

500건은 빠르게 “열 수 있는지”를 보기 좋지만, USN 열거 순서 때문에 **초반에 치우칠 수 있습니다.** 큰 샘플에서는 전체 MFT를 두 번 읽지 않고, 서로 다른 파일 FRN에 **stride**(예: 5k→3, 10k→5, 50k→10)를 두어 구간을 넓힙니다. 무작위 표본은 아닙니다.

UI는 직전 트리 진단의 `FileRecords`와 샘플의 `FilesPerSecond`로 **대략적인** 전체 조회 시간을 표시할 수 있습니다. 권한·캐시·부하에 따라 달라지며, 실제 전 볼륨 집계를 실행한 결과는 아닙니다.

### 이후 방향(검토만)

- 대량 샘플에서도 files/s와 성공률이 안정적이면, **제한된 범위의** 전체 크기 조회를 검토할 수 있습니다.
- 그렇지 않으면 raw MFT 속성 파싱 등 다른 경로를 조사하거나, NTFS 경로는 구조·속도 진단용으로만 쓸 수 있습니다.

## 정리 후보와의 관계(경로 매핑 PoC)

- 정리 후보의 **표시 경로**(`C:\…`, `%TEMP%` 등)는 USN 레코드의 **이름·FRN**과 바로 같지 않습니다. 후보 폴더를 NTFS 쪽에서 다루려면 **경로 → FRN 체인**을 맞추는 단계가 필요합니다.
- 앱에는 **`NtfsPathMappingProbeService`**가 있으며, **마지막 경로 세그먼트**가 같은 레코드를 후보로 잡고, **ParentFRN**을 따라 올라가며 위쪽 세그먼트와 일치하는지 확인합니다. 전 레코드에 full path 문자열을 붙이지 않습니다(메모리·속도).
- 이 진단은 **매핑 가능 여부**만 보고, **크기 합산·OpenFileById 전체 조회·하위 subtree 집계**는 하지 않습니다.
- 설계 배경은 [NTFS_CLEANUP_CANDIDATE_INTEGRATION.md](NTFS_CLEANUP_CANDIDATE_INTEGRATION.md)를 참고합니다.

### 다음 단계 후보(아직 미구현)

- raw MFT 속성 파싱 등 다른 전략과의 비교
